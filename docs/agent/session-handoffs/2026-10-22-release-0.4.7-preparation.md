# LUMA Remote 0.4.7 release preparation

## Goal

Build and deploy an update-compatible APK so the new remote controls and subtitle
repair can be tested on the phone and receivers.

## Files inspected

- Required agent documentation and the prior 0.4.6 release handoff.
- `docs/releasing.md`, Android Gradle configuration, release build/publish scripts,
  release notes and local toolchain availability.
- Local keystore candidates by public certificate only; no credential value was
  copied into the repository.

## Files changed

- `android/app/build.gradle`: version 0.4.7/code 17.
- `release-notes/0.4.7.txt`: remote, system-next and subtitle repair notes.
- `Makefile`, `scripts/release-next-android.mjs` and focused tests: guarded
  one-command next-version release plus an explicit page-only target.
- `README.md`, `docs/releasing.md` and release architecture documentation.
- Current state, index, log and this handoff.

## Commands run

- Pinned Gradle 9.6.1 offline `:app:assembleDebug` — passed after allowing Gradle
  to load its native library outside the sandbox.
- `aapt2 dump badging` — package `dev.framextv.lumaremote`, version 0.4.7/code 17,
  min SDK 24 and target SDK 35.
- `apksigner verify --print-certs` and SHA-256/size inspection — the built APK is
  validly debug-signed, 10,764,705 bytes, SHA-256
  `e38827ac4b5fabe841a3bf2bc3595c5202eec97e555b214e7cc740f8ed8f48cc`.
- Read-only certificate verification — the legacy local release keystore matches
  `android/release-certificate.sha256`.
- Focused next-release, manifest and Pages tests — 10 passed.
- Full `npm test` outside the restricted localhost sandbox — 246 passed. The
  first sandboxed run was interrupted after localhost-listener tests failed to
  bind and left workers waiting.
- `node --check scripts/release-next-android.mjs`, `make -n deploy-gh-pages`,
  `make -n deploy-page` and `git diff --check` — passed.

## What worked

- The actual Android Gradle project compiles and packages the complete feature
  set as 0.4.7/code 17.
- The production certificate can be identified without changing the app's update
  identity.
- `make deploy-gh-pages` now owns exact next-patch/code planning, staged-source
  checks, tests, signing, commit/push, publication and page deployment. It keeps
  page-only recovery under `make deploy-page` and auto-stages bounded allowlisted
  new text files while leaving unrelated untracked files untouched.
- The release target itself was not invoked: no commit, push, GitHub release or
  Pages deployment was performed during this preparation.

## What failed

- The first sandboxed Gradle attempt could not load its native library; the
  approved offline rerun passed.
- Production signing was initially paused at the security boundary because its
  keystore and credential are sourced from a sibling project. The user later
  configured that intended signer privately through the ignored local config.
- The debug APK cannot update an installed public/production-signed app.

## Remaining questions

- Retry the one-command release, then verify the public APK/feed and physical
  update without exposing the saved signing configuration.
